# SyncWatch development instructions

- Treat SyncWatch as a standalone product. Keep project code in this checkout.
- The canonical repository is `salo-group/syncwatch`. Target pull requests and merges to its `main` branch. Forks may host working branches; they are not merge destinations. Use `--repo salo-group/syncwatch` with GitHub CLI commands and verify the pull request's base repository before merging.
- Write repository documentation in English. Keep application usage, installation/build instructions, product requirements, design, architecture, and reusable project skills in this checkout. Use repository-relative links and declared dependencies.
- Keep implementation and pull-request plans, development-process instructions, debugging notes, local verification reports, logs, screenshots, and session history outside the checkout. Product documentation and these instructions must not depend on or link to an external workspace, device inventory, or local report.
- Follow the product requirements in `docs/architecture/product-requirements.md` and the design contracts in `packages/design/`. Record provider limitations and unmet requirements explicitly.
- Preserve the screens, controls, settings, window behavior, localization, and media lifecycle specified in `docs/application.md`. A platform or engine change must not silently remove documented behavior or replace a functioning control with a mock.
- Use Swift for Apple clients, C# for Windows, VLC/libVLC for playback, Syncplay for playback synchronization, and Google Meet for calls in a separate app-owned window. The platform-neutral design library is `packages/design/`, using Apache 2.0 Style Dictionary to generate native resources. Follow `docs/architecture/README.md` and its unresolved feasibility gates.
- Add every external source dependency as a pinned Git submodule under `3rdparty/`; do not copy vendor sources or silently fetch runtime dependencies through package managers. Record transitive dependencies and SDK/runtime exceptions in `docs/architecture/dependencies.md`.
- Never commit credentials, meeting invitations, local device configuration, runtime logs, binaries, caches, or build outputs.
- Commit and push each completed meaningful change. Validate changed files and report checks that have not run.
- Preserve the required CI checks in `.github/workflows/`; add real build/test coverage with executable components and do not mask failures or report unavailable integrations as passing.
- Repository validation runs with `python3 tools/ci/check_repository.py`; CI tooling tests run with `python3 -m unittest discover -s tools/ci/tests -v` and `node --test tools/ci/tests/artifact_upload.test.mjs`.
- Shared schemas and acceptance fixtures live in `contracts/`. Initialize only the pinned validator with `git submodule update --init --checkout --depth=1 -- 3rdparty/fastjsonschema`, then run `python3 tools/contracts/check_contracts.py` and `python3 -m unittest discover -s tools/contracts/tests -v`. Keep wire semantics in `docs/architecture/contracts.md` aligned with the schemas and reference checks.
- Dependency builds use `tools/dependencies/components.json` and `tools/dependencies/build.py`. Run `python3 -m unittest discover -s tools/dependencies/tests -v` and `node --test tools/dependencies/tests/cache.test.mjs`. Register each complete source graph and real offline recipe before marking it ready; unavailable components cannot be reported as passing.
- Native shells live in `apps/apple/` and `apps/windows/`; their UI-independent modules and focused tests live in `packages/apple-domain/` and `packages/windows-domain/`. Follow `tools/native/toolchains.json`, `global.json`, `.swift-format`, and `.editorconfig`. See `docs/building.md` for self-contained build and launch commands; media, synchronization, calls, and complete shared-design UI remain planned.
